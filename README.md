# P&ID → Graph Conversion & SOP Cross-Referencing

Converts a P&ID diagram into a structured, attributed graph and cross-references it
against an SOP document to flag discrepancies.

## Install

```bash
pip install -r requirements.txt
```

Tesseract OCR must also be installed as a system binary (pytesseract is just a wrapper
around it):

```bash
sudo apt-get install tesseract-ocr   # Debian/Ubuntu
brew install tesseract                # macOS
```

## Run

```bash
python main.py --pid data/pid/diagram.pdf --sop data/sop/sop.docx --out output/
```

Outputs written to `output/`:

- `pid_graph.json` / `pid_graph.graphml` — the extracted component graph (NetworkX)
- `cross_reference_report.json` / `.log` — discrepancies found, ranked by severity

## Test

```bash
python -m pytest tests/ -v
```

19 tests, happy/edge/failure path per module. The integration test runs the full
pipeline against the synthetic fixtures and asserts every discrepancy category the
fixture was designed to trigger actually fires — and that the one SOP-stated
connection matching a real P&ID edge is correctly *not* flagged.

## Sample / Synthetic Data

`data/pid/diagram.pdf` and `data/sop/sop.docx` in this repo are **synthetic
placeholders**, generated by `scripts/generate_sample_data.py` — not the real
assignment files. They exist so the pipeline has something to run against and so
every discrepancy type is provably exercised end-to-end. Drop the real files at
those same two paths to run against them; nothing else changes.

Regenerate the synthetic fixtures with:

```bash
python scripts/generate_sample_data.py
```

The synthetic scene is a 4-component chain (`T-101` tank → `P-101` pump → `V-101`
valve → `FT-101` instrument) plus a few deliberate traps: an isolated `V-102` valve
never mentioned in the SOP, an unlabeled symbol with no readable tag, an SOP
reference to a `PSV-201` that doesn't exist in the diagram, an SOP line that
mislabels `T-101` as a "pump," and an SOP-stated connection between two tags that
aren't actually connected. See the module docstring in `generate_sample_data.py`
for the full list — each trap maps to one discrepancy category below.

## Approach & Assumptions

**No labeled P&ID symbol dataset is available for this assignment**, so training or
fine-tuning a detector (YOLO et al.) wasn't a realistic option in the time available.
Instead this uses classical CV — OpenCV contour/shape heuristics plus Tesseract OCR —
which is fully deterministic, requires no training data, and is transparent about
*why* it classified something a given way. The tradeoff: it assumes reasonably
clean, stylized diagrams (solid-fill symbols, machine-printed tags, mostly-straight
connector lines) rather than noisy hand-marked scans. The path to upgrading this to a
trained detector is narrow and contained: `shape_detection.detect_shapes()` is the
only place that would change — everything downstream (OCR tagging, connector
detection, graph building, cross-referencing) consumes its `DetectedShape` output
and is agnostic to how those shapes were found.

**Pipeline:**

```
PDF → image (PyMuPDF)
    → shape detection (OpenCV contours: rectangle=tank, circle=instrument,
      circle+child-triangle=pump, notched/concave polygon=valve)
    → OCR tag extraction per shape (Tesseract, cropped label region below/around
      each symbol, regex-normalized against ISA tag format e.g. "FT-101")
    → connector detection (mask out symbol interiors, Hough line detection on
      what's left, attach each segment's endpoints to the nearest symbol)
    → NetworkX graph (nodes = components with {tag, type, bbox, symbol_kind},
      edges = detected connections)

SOP .docx → plain text (python-docx)
    → tag extraction (same ISA regex)
    → declared-type extraction ("valve V-101", "pump T-101" → type claims)
    → stated-connection extraction ("X connects to Y", "X feeds into Y", ...)

Cross-reference → discrepancy report (severity-ranked: ERROR/WARNING/INFO)
```

**Key design decision — connector detection:** an earlier version sampled straight-line
"ink coverage" directly between every pair of shape centers. That produces false
positives for three inline connected components (A–B, B–C) reading as a spurious
direct A–C edge, since the line between A and C's centers passes straight through B's
solid body. The current approach instead masks out all symbol interiors first, runs
Hough line detection on the remaining pixels (pipe strokes only), and attaches each
detected segment's two endpoints to the nearest symbol — so a line only ever connects
the two symbols it actually touches. Assumption: pipes are mostly straight-line runs;
multi-bend orthogonal routing is a known gap (see Limitations).

**Discrepancy categories:**

| Category | Severity | Meaning |
|---|---|---|
| `MISSING_IN_PID` | ERROR | SOP references a tag not found in the diagram |
| `CONNECTION_MISMATCH` | ERROR | SOP states two components connect; no such edge was detected |
| `TYPE_MISMATCH` | WARNING | SOP describes a component's type differently than the diagram classified it |
| `UNRESOLVED_TAG` | WARNING | A symbol was detected but OCR couldn't read its tag — needs manual review |
| `MISSING_IN_SOP` | INFO | A diagram component is never mentioned in the SOP (informational, not necessarily wrong) |

**Tag typing:** a component's type is read from its ISA tag prefix when OCR succeeds
(e.g. `FT-` → flow transmitter, `V-` → valve, `PSV-` → safety valve — see
`src/component_types.py`), falling back to the shape classifier only when no tag was
read. Tag prefix is treated as authoritative because it's the actual engineering
data; shape classification is the best-effort fallback.

## Limitations (honest, not hidden)

- Connector detection assumes straight or near-straight pipe runs. A diagram with
  heavy orthogonal routing (multiple 90° bends) would need real line-segment
  tracing/merging, not single Hough segments.
- Shape classification is heuristic (contour geometry), not a trained detector — it
  will misclassify or miss symbols that don't match the assumed conventions (solid
  fill, closed outline, tag adjacent to symbol).
- OCR tag matching is regex-anchored to ISA-style tags (`[A-Z]{1,4}-\d{2,4}[A-Z]?`).
  Diagrams using a different tag convention would need that pattern updated in one
  place (`src/component_types.py::TAG_CORE`).
- SOP relation extraction (`"X connects to Y"`) is phrase-pattern matching, not full
  NLP — it will miss connections stated in less templated language. Given more time,
  this is the piece I'd hand to an LLM-assisted extraction pass instead of regex.

## Bonus not attempted (time-boxed)

Web UI visualization and DB-backed storage were left out to prioritize a correct,
tested, well-documented core pipeline within the assignment's time expectations. The
NetworkX graph already exports to JSON/GraphML, so a visualization layer (e.g.
pyvis/D3 reading `pid_graph.json`) is a bounded follow-on, not a rearchitecture.
